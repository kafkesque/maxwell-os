# T-120 step 0 — the corroboration FALSIFIER, run read-only, and what it fired

**Date:** 2026-10-14 · **Mover:** pipeline · **Gate:** READ-ONLY step 0 (T-120) · **No store write.** Every number
below is a read (`file:…?mode=ro`) of the live store and of three pre-images; nothing was computed by writing.

**Why this measurement exists.** D-2992 R1 declared corroboration a MEASURE re-derived from a row's own evidence, and
attached its own FALSIFIER to the ruling, verbatim:

> "Its FALSIFIER is part of the ruling: if `P(n_voices >= 2 | is_convergent = 1)` is indistinguishable from 1, the
> count is NOT contaminated in this corpus and the hardening is documentation."

An unfalsified falsifier is a belief. This record runs it.

---

## 1. The falsifier, run

**Population:** the DECLARED population — `pipeline.pipeline_paths.CANONICAL_RUN` = `rechunk-v4-20260929`, table `fbs`,
7,640 rows (the whole table; every row carries that `pipeline_run_id`). `n_voices` = distinct canonical
`source_ids` per row (D2185/D2309 works, not filenames — the D-2590/BUG-468 defect class).

| quantity | measured |
|---|---|
| **P(n_voices ≥ 2 \| is_convergent = 1)** | **1,393 / 1,393 = 1.0000** |
| P(n_voices ≥ 2 \| is_convergent = 0) | 0 / 6,247 = **0.0000** |
| rows with `source_ids` NULL or empty | **0** (of 7,640) |

**Verdict: THE FALSIFIER FIRED.** The count is not contaminated — it is *exact*, in both directions. `is_convergent`
is a bit-for-bit function of "does this row carry ≥2 canonical works", so on this corpus the count dimension of
corroboration carries **no information that `source_ids` does not already carry**.

**What that means, and what it does NOT mean.**

- It does NOT mean corroboration is fake. The principle is satisfied by real evidence: 1,393 rows are corroborated
  by two or more independent works, and 938 of them are served (`PASS`).
- It DOES mean the expensive half of the T-120 mechanism is **not needed for this corpus**: re-clustering
  `source_segments` by embedding similarity and confirming with NLI in order to recover a second voice in the row's
  own evidence would re-derive a number the row already states. That half of the hardening is DOCUMENTATION on this
  corpus, exactly as D-2992's own falsifier said it would be if it fired.
- It DOES mean the corroboration MEASURE's information lives entirely on the **independence axis** — which is what
  `isor` (D2284/D2309) already computes and which no surface advertises.

**The consequence, stated as a rule rather than a preference.** The engine T-120 was going to build is the wrong
engine for this store: the correction needed is not "re-count the voices", it is "publish the independence of the
voices you already count". That is the T-107/T-118 change-set (BUG-767), not a re-clustering job.

## 4. The feedback loop: the ledger is LAZY, and that is the correct reading (not a bug)

`fb_feedback` does **not** exist in the live store. It is created by `pipeline/feedback.py:118`
(`CREATE TABLE IF NOT EXISTS`), i.e. **on first write** — and no rating has ever been recorded, which is why the
cache (`feedback_score` / `feedback_count`) is NULL / 0 on every row. That is exactly the declared absence shape
(D-2957, `config/feedback.yaml#absence`): ABSENT, never 0.0. **The feedback loop is in a correct state today**, and
the parity rail (`scripts/check_feedback_parity.py`) therefore passes trivially.

The risk is the FIRST rating: it is the moment the cache becomes non-trivial and the wire shape becomes visible. The
two owed repairs (publish `{score, count, state, prior, effective}`; move the `pipeline/retrieve.py` neutral-prior
literal into `config/feedback.yaml`) should land BEFORE that first write, so the transition is declared rather than
discovered (T-107).

## 5. The dedup question, answered with the store rather than with reasoning

The owner's gate question was: *does the corroboration change guarantee no duplicates after S4/S5?* Measured here:

| check | measured |
|---|---|
| duplicate `fb_id` (the S6 primary key) | **0 of 7,640** |
| `duplicate_of` non-null (the D-2951 marker) | **0** — and that is the CORRECT state (0 link candidates on the faithful S6 input; `config/store_columns.yaml:99`) |
| normalized-name collisions (same `name`, >1 `fb_id`) | **3 groups / 6 rows** — `vj performance method`, `item validation protocol`, `design thinking process` |
| where those 6 rows live | **all 6 are `QUARANTINE`; ZERO are served (`PASS`)** |
| their source work | 2 of the 3 groups are the **SAME** `source_id` (a single work read twice → `dedup_identity.classify_group` = `same_source_collide`); 1 group is two DIFFERENT works sharing a generic name (legitimate, not a duplicate) |

**Conclusion, in both directions.** In the SERVED population there is no duplicate residue at all: the name-collision
residue sits entirely in the quarantine lane that T-117 is the gate for, and 2 of the 3 groups are the
same-source-collision class the ALIAS-LAYER-RETIRED cause already names. Corroboration is therefore not, and was
never, the dedup guarantee — dedup is S1.5 (cluster-before-extract) + `dedup_identity.classify_group` +
`dedup_gate` + the S6 `fb_id` primary key, and it holds. What corroboration owns is the TRUST statement about a row,
which is exactly why the tier (T-118) and the false 0.0 (BUG-767) matter and why neither is a dedup fix.
