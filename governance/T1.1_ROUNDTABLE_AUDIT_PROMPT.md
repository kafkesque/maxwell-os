## 2. Your mandate — the failure-mode checklist

Audit for **any** of the following, in order of priority. For each finding, state severity
(`BLOCKER` / `HIGH` / `MEDIUM` / `LOW` / `INFO`) and the specific file/decision implicated.

1. **Hidden failure** — any code path that can fail silently or produce wrong output without erroring.
2. **Error / crash** — any input, edge case, or sequence that can raise an uncaught exception.
3. **Leak** — memory, file-handle, connection, or data leak (see G10 wired-memory test below).
4. **Contamination** — stale state, cross-run bleed (run_id/checkpoint caching), or data from a
   prior run polluting a new run.
5. **Bug** — logic error, off-by-one, wrong field name, wrong model, wrong path.
6. **Contradiction** — two components/decisions that conflict (e.g. config vs code, doc vs code).
7. **Gap** — a needed capability that is absent or unwired (e.g. declared-but-not-integrated).
8. **Conflict** — model-family/rule violation (R5 generator≠verifier), overlapping writes.
9. **Blindspot** — a region not covered by tests/gates (e.g. a content type, a failure mode).
10. **Bloat tax** — dead code, unused config, redundant passes (C19/C28).
11. **Future-tax mismatch** — a shortcut now that forces expensive rework later (C27).
12. **Inconsistency** — schema drift, naming drift, threshold drift between config/code/docs.
13. **Risk / threat** — anything that jeopardizes data integrity, sovereignty, or reproducibility.
14. **Bottleneck** — a serialized/stale step that makes the full run infeasible (time/memory).
15. **Drift** — calibration/threshold/metric that no longer matches reality after recent fixes.

## 4. The four seats — adopt each POV and audit from it

**Seat 1 — Senior Knowledge Architect.** Is the *knowledge* trustworthy? Are the FBs faithful,
non-redundant, well-scoped, and correctly classified? Is the verify gate's precision/recall
trade-off acceptable for a production knowledge base? Are ISOR/epistemic-status/confidence
fields coherent and actually meaningful to a downstream consumer?

**Seat 2 — Senior RAG Engineer.** Will this knowledge base *retrieve well*? Are chunks/clusters/
FBs at the right granularity? Are embeddings and dedup sound? Will the 24.5% convergence rate
produce a usable graph, or a sparse one? Is sqlite-vec degradation acceptable? Are the
quarantine-as-tier semantics correct for retrieval (quarantined ≠ deleted)?

**Seat 3 — Senior Software Engineer.** Will this *run without crashing* for ~26h over hundreds
of books? Check: resume/checkpoint idempotency, run_id caching, timeout handling, exception
paths, memory (G10: wired flat 34.07→34.07 GB, 0.0% growth, 0 errors — is that sufficient
evidence?), file-handle hygiene, crash-safe writes, partial-failure recovery, and the
`call_llm`→`None` handling that caused PROBE ABORT earlier.

**Seat 4 — Senior Agentic Engineer.** Are the model assignments and failure modes sane? Is the
generator≠verifier separation (R5) actually held across every stage? Is the reasoning-model
`reasoning_content` passthrough hazard fully contained (DELEGATE-001, D2319)? Are the
`temperature=0.0` and `$0 marginal cost` guarantees intact? Is the fail-closed behavior correct
everywhere, or are there fail-*open* paths?

## 5. Required output format

For each seat, produce:

1. **Top 5 findings** (ordered by severity), each with: severity, evidence, file/decision,
   and a concrete fix or "accept with rationale".
2. **A GO / NO-GO / CONDITIONAL-GO verdict** for T1.1, with the single most important
   condition if CONDITIONAL.
3. **One thing the other three seats are likely to miss.**

Then a **consensus risk register**: a table of every finding across seats, deduplicated,
sorted by severity, with an owner (which component/stage) and a pre/post-T1.1 disposition.

**Ground rules:** be adversarial but evidence-based — do not invent bugs. If you cannot confirm
a suspicion without running code, say so explicitly and state what you would run to confirm it.
Prefer concrete file/line/decision references over generalities.
