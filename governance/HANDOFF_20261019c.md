## 2. EFFICIENCY DESIGN — why 10min/query + human, and the token-optimized fix

**Why slow**: 32K window + `max_compactions_per_session` hit at 0.94 → lossy compaction eats time; single serial brain; human gated every step.

**The design (token-optimized, no overengineering):**
1. **Hand off, don't compact.** Config already prefers `declared_handoff_first` over in-place compaction. Compaction is lossy+slow; a session-resume handoff file is a deterministic lossless write. Use the `session-resume` skill / `governance/session_plan_*.yaml` instead of hitting compaction.
2. **Parallel fan-out, serial only where dependent.** Delegate sub-steps in parallel to the D-2549 routing map:
   - loop driver (latency-critical): MiniCPM5-2B (2.1s) or Ornith-1.5-9B (11.5s)
   - classification / summarisation WITH source / code review: gemma-4-E4B (0.48s)
   - single-shot code gen: Qwen3-Coder-30B (one-shot, 34.5 tok/s)
   - brain/coordination: gpt-oss-20b (local, $0) — escalate to deepseek-v4-pro ONLY when gpt-oss would slop/drift (D-3023, owner-gated BUG-832 remedy #2)
   - deterministic data-repair (SQL/FTS/scripts): EXECUTE directly, LLM-free.
   Wall clock → max(subtask) + merge, not N×serial.
3. **Shrink before it grows.** stage1_3 prefilter + stage1_5 cluster-before-extract mean the brain sees convergent facts, not raw 32K of dross.
4. **Human only at owner-gates** (D-2898 promotion, D-3035 open owner-lane approval, D-3036 red-loop receipt, destructive writes, cloud escalation). Everything else runs unattended with `scripts/delegate_journal.py` (T-168) as the audit record — the journal IS the human's substitute for routine steps.
