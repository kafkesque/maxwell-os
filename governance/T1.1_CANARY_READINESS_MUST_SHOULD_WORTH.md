## ⚙️ S4 Bottleneck — the ultimate solution (D2354)

**Root cause (verified, not assumed):** `gpt-oss-20b-MXFP4-Q8` is a reasoning model (~1165 chars `reasoning_content` before the answer, needs `max_tokens ≥ 1024`). D2249 swapped Phi→GPT-OSS for depth accuracy (38%→87.5%) at ~5–10× latency. S4 runs **two GPT-OSS workloads/FB**: batch CRIBS/classification (amortized ~15s/FB) + focused depth (serialized ~10s/FB) ≈ **25s/FB**.

**Correctness-first, then remove waste, then optimize (gated):**

```
PHASE 0 — CORRECTNESS (M1+M2, blocking)
├─ fail-closed depth (no silent "domain")
├─ depth_max_tokens 512 → 1024
└─ exact-token parser (accept exactly 1 of 4 labels)

PHASE 1 — REMOVE WASTE (no quality risk)
├─ remove `depth` from CRIBS batch schema/prompt (don't pay for discarded work)
└─ batch the FOCUSED depth prompt (4–8 FBs/request)
     → keep GPT-OSS + SHORT prompt + fb_index→result ordering
     → do NOT reuse the long-prompt batch depth (that's the 38% path)

PHASE 2 — OPTIMIZE (gated on benchmark)
├─ golden set through BOTH single focused call (A) and focused batch (B)
├─ gate: B vs A ≥90% agreement + zero malformed + zero silent failures
└─ only then: candidate gemma-4-E4B (non-reasoning, ~5s, different family)
     → R5-compatible: Qwen(gen) / GPT-OSS(classify) / Gemma(depth)
     → hold behind the SAME ≥90% gate, through the PRODUCTION path
```

**Target architecture:**

```
S4 FB ──┬── GPT-OSS CRIBS/classification batch   (no depth)
        └── GPT-OSS focused-DEPTH batch           (fb_index ordered)
                  ↓
              optional Gemma swap after benchmark gate
```

**Expected:** ~17s/FB → ~6–8s/FB from batching the focused depth alone (zero accuracy change); full T1.1 ≈ 62h → ~25–30h.

**Why not "just swap to Gemma":** a model swap is a *quality-risk* decision, not a performance decision. The ontology (4-way depth) is already sound; the short prompt is already clean. Batch the proven prompt first, benchmark, then consider the cheaper model. No router framework, no distillation, no serving rewrite required for T1.1.

### ⚙️ S4 bottleneck A/B result (D2354) — live, n=8, seed=42

| Path | Total | Avg/FB | Accuracy | Parity | Failures |
|---|---|---|---|---|---|
| A — sequential `classify_depth_focused()` | 67.4s | 8.4s | 75.0% | — | 0 |
| B — `batch_depth_classify()` (batch=4) | 34.8s | 4.3s | 75.0% | 75.0% | 0 |

**Verdict: batching does NOT pass the D2354 gate.** Speedup is ~1.9× (not the projected
6–8×), and A↔B parity is 75% (below the ≥90% gate) — batching the depth prompt flips 2 of 8
decisions (`CONV-053` B-correct/A-wrong; `CONV-049` A-correct/B-wrong). Both paths hold 75%
accuracy, so batching is a wash on correctness but introduces decision drift. **Not adopted
into production.** Report: `governance/s4_bottleneck_ab_test.md` (+ `.json`).

**Implication:** GPT-OSS reasoning cost does NOT fully amortize across a batch (the model
reasons per-FB), and batching perturbs the answer. The higher-leverage move is the
FrugalGPT cascade: route the one-word depth call to `gemma-4-E4B-it-MLX-4bit` (non-reasoning,
~5s, different family = R5-clean) — still behind the same ≥90% benchmark gate, through the
production path. `batch_depth_classify()` remains available (feature-flagged, unused).
